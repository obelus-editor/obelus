Feature branch
----
The agent works on a branch in a worktree of its own under .worktree, and tells you where to try it and what it ran, offering to start it if it can. Once you accept it, it asks whether to review it, then whether it goes back as a merge or a pull request or waits for later. A pull request is merged when its checks pass -- by you, from a link it gives you, where `gh` is not installed and signed in -- and then it asks whether to bring your checkout up to it, if that is the branch you are on. The worktree is taken away only when you say so.
----
This project changes its files on a branch of their own. When you are about to change any of this repository's files, do the work in a worktree of its own rather than in the checkout the reader is reading. Reading needs none, and neither do Obelus's notes or files outside the repository. One worktree is enough for one conversation: once you have made it, every later change goes there too. If `git rev-parse --show-toplevel` says this is not a git repository, there is no branch to work on: change the files where they are, say so, and the rest of this does not apply.

Make it from the root of this checkout. First note which branch the checkout is on: that is the branch this work goes back to, and the base of anything you compare it with. If the checkout is on no branch, ask which one the work is for. Make sure `.worktree/` is ignored: if `git check-ignore -q .worktree/` says it is not, add it to the file at `git rev-parse --git-path info/exclude` -- that file is this clone's own, where `.gitignore` is the project's and goes to everybody. Then `git worktree add -b <branch> .worktree/<branch>`, naming the branch after the change. If you have a tool that moves your own working directory into an existing worktree by its path, use it; one that makes a worktree somewhere of its own choosing is not that tool. Otherwise use the worktree's paths, and run its commands there. The reader's checkout is theirs: nothing in it changes until they say so.

Before changing anything, get the worktree ready the way the project builds -- its dependencies installed, if it has any to install -- and run its tests once, so that a failure afterwards is known to be the change's. If they already fail, say which, and ask whether to go on.

When the change is made, run the tests again and say where it is -- the directory and the branch -- so the reader can go there and try it however they try this project. Say what you ran and what it showed, not that it should work. Commit in the worktree; nothing leaves it yet. Then ask, on a card, how they will try it. If you know how the project is run -- its own instructions say, or its manifest names a command -- and it runs without a terminal of its own, such as a window or a server you can start in the background, offer to start it from the worktree beside trying it themselves. A program that draws in the terminal it is started from cannot be given one by you: give its command instead, and do not offer. What you start, you stop -- once they have tried it, before anything is reviewed or merged, and before the worktree is removed -- by the process you started and never by its name. Ask nothing about what comes after -- not the review, not where it goes -- until they say they have tried it: a question about a review put beside "here it is" is a question about a change nobody has looked at, and it reads as the agent hurrying them past the trying.

When the reader says they have tried the change and are satisfied with it, ask whether to review it before it goes anywhere. If they say yes, review `git diff $(git merge-base <base branch> HEAD)..HEAD` -- in a fresh context if you can start one, such as a subagent given only the diff, what the change is for and the note this conversation is about where there is one, and yourself otherwise. The review reads and changes nothing: no checkout moves and no file is written. Check each finding against the code before reporting it, report them by how much they matter -- what is wrong, what should be fixed before it merges, what could wait -- and say plainly whether it is ready to go. Ask which to fix, as a list they can tick several of, and fix them one at a time, running the tests after each. A fix changes what the reader accepted, so afterwards say what changed and let them try it again before going on.

Then run the tests in the worktree once more. If they fail, say so and stop: what becomes of a change is asked about a change that passes. Otherwise ask what becomes of it: a merge into the base branch, a pull request against it if the repository is on GitHub, or keeping the branch as it is for later. Before offering a pull request, run `gh auth status`: `gh` is how one is opened, followed and merged, and that one command says both whether it is installed and whether it is signed in. If it fails, offer the pull request all the same, as one that ends with a link, and say on the card why. A project whose own instructions say how changes reach its branches has already answered part of that, so offer only what it allows.

A merge is made in the reader's checkout, so look at it first. If it is not on the base branch, do not switch it: say so and ask. If it has changes of its own, say so and stop -- do not stash or reset them. After the merge, run the tests on what it made; if they fail, stop and leave the worktree and the branch where they are -- nothing has been pushed, so nothing is lost. Pushing the merged branch is a second question.

A pull request: push the branch, open it against the base branch with `gh pr create`, following the repository's own template where it has one, then follow its checks with `gh pr checks --watch`. When they pass, merge it with `gh pr merge`, the way this repository's history says it merges. When one fails, say which and why -- `gh run view --log-failed` has the reason -- and ask whether to fix it in the worktree before pushing again. A push that is refused means the remote has moved: find out how, and force it only if the reader asks you to. The worktree stays until the pull request has merged, because that is where a fix to it is made.

A pull request without `gh`: push the branch all the same, and give the reader the link to open it themselves -- the one `git push` printed, or the repository's `compare/<base>...<branch>` page. Say why it is theirs to open -- `gh` is not installed, or is not signed in -- and that following its checks and merging it are theirs too; it has merged when they say it has. And say what `gh` would do for them: with it installed and signed in with `gh auth login`, you open the pull request, follow its checks, say why one failed and merge it yourself, which is worth knowing before the next one. Do not install `gh`, sign it in, or reach GitHub some other way with a token you found: each is done to the reader's machine or in their name, and they asked for none of it.

Kept for later: say where the worktree and the branch are, and leave both.

A pull request that has merged has moved the base branch on the remote and not in the reader's checkout. So once one has -- whether you merged it or the reader says they did -- look at the checkout. If it is on the base branch, ask whether to bring it up to date with `git pull --ff-only`. Only a fast-forward: if the base branch has commits the remote does not, say so and stop, because merging or rebasing them is the reader's. Changes of their own do not stop it, because git refuses a fast-forward that would overwrite one; if it refuses, say which files and leave them as they are. If the branch has no upstream, say so rather than setting one. If the checkout is on another branch, do not switch it: say that the base branch has moved on the remote, and ask nothing.

Once it is merged, ask whether to remove the worktree. If yes, run `git worktree remove` from the root of the reader's checkout rather than from inside the worktree, then `git worktree prune`, and delete the branch -- with `-D` if the pull request was squashed, because git cannot see that a squashed branch has merged and the pull request already says it has. If the removal is refused, the worktree holds files that exist nowhere else: list them with `git -C <worktree> status --porcelain -uall` and ask whether to commit them, move them into the reader's checkout, or delete them. Never remove it with `--force` on your own judgement.

The work is thrown away only when the reader asks for that in so many words, and only after saying what goes with it -- the branch, its commits and the worktree -- and hearing them confirm.

Every one of these questions is the reader's, and each goes on a card: asked with your own tool for asking the user a question, which reaches Obelus as `elicitation/create`.
