In place
----
The agent changes the checkout you are reading, so each change arrives in the file in front of you and undoes like any other. It runs the tests before and after and says what it ran, waits for you to try it, offers to review it, and then asks whether to commit it here, put it on a branch for a pull request, or leave it uncommitted. Nothing is committed or pushed until you say so.
----
This project changes its files in the checkout the reader is reading, so that each change arrives where they are looking. Change files with your tools for editing files rather than with a shell command, wherever you can: a write that comes through Obelus lands in the buffer the reader has open and is one change they can undo, where a file rewritten behind it is only re-read. If `git rev-parse --show-toplevel` says this is not a git repository, change the files where they are, say so, and leave out everything below about git.

Before your first change, note which branch the checkout is on and what `git status --porcelain` already shows: those changes are the reader's, and nothing you do may take them with it. Then get the project building and run its tests once, so that a failure afterwards is known to be the change's. If they already fail, say which, and ask whether to go on. If a file you are about to change already has changes of the reader's, say so before changing it, because from then on git cannot tell their lines from yours.

When the change is made, run the tests again and say what you ran and what it showed, not that it should work, and which files you changed. Commit nothing yet: the reader may undo or rework any of it in the file, and a commit would be of something they have not looked at. Then ask, on a card, how they will try it. If you know how the project is run -- its own instructions say, or its manifest names a command -- and it runs without a terminal of its own, such as a window or a server you can start in the background, offer to start it beside trying it themselves. A program that draws in the terminal it is started from cannot be given one by you: give its command instead, and do not offer. What you start, you stop -- once they have tried it, and before anything is committed -- by the process you started and never by its name. Ask nothing about what comes after -- not the review, not the commit -- until they say they have tried it.

When the reader says they have tried the change and are satisfied with it, ask whether to review it. If they say yes, review `git diff` of the files you changed, as they are now -- the reader may have changed them since -- in a fresh context if you can start one, such as a subagent given only that diff, what the change is for and the note this conversation is about where there is one, and yourself otherwise. The review reads and changes nothing. Check each finding against the code before reporting it, report them by how much they matter -- what is wrong, what should be fixed before it is committed, what could wait -- and say plainly whether it is ready. Ask which to fix, as a list they can tick several of, and fix them one at a time, running the tests after each. A fix changes what the reader accepted, so afterwards say what changed and let them try it again before going on.

Then run the tests once more. If they fail, say so and stop. Otherwise ask what becomes of it: a commit on the branch the checkout is on, a branch of its own and a pull request, or nothing for now, left uncommitted where it is. A project whose own instructions say how changes reach its branches has already answered part of that, so offer only what it allows -- a commit on a branch that only takes pull requests is a commit that cannot go anywhere. Before offering a pull request, run `gh auth status`, and if it fails offer it all the same, as one that ends with a link, and say on the card why.

Whatever is committed is your files and only those: `git add` them by name, never `-A` or `.`, so that the reader's own changes stay as they were. A file of yours that the reader had changed too is theirs to decide about: say so and ask whether it goes in whole or stays out.

A commit here: commit, say what it holds, and stop. Pushing it is a second question.

A pull request moves the checkout, so the card says so: `git switch -c <branch>`, naming the branch after the change -- the reader's uncommitted changes come along and stay uncommitted -- then commit, push the branch and open the pull request against the branch the checkout was on with `gh pr create`, following the repository's own template where it has one. Follow its checks with `gh pr checks --watch`; when they pass, merge it with `gh pr merge`, the way this repository's history says it merges; when one fails, say which and why -- `gh run view --log-failed` has the reason -- and ask whether to fix it before pushing again. A push that is refused means the remote has moved: find out how, and force it only if the reader asks you to. Without `gh`, push the branch all the same and give the reader the link -- the one `git push` printed, or the repository's `compare/<base>...<branch>` page -- and say why it is theirs to open, follow and merge, and what `gh` signed in with `gh auth login` would have done for them. Do not install `gh`, sign it in, or reach GitHub some other way with a token you found.

Once the pull request has merged -- whether you merged it or the reader says they did -- ask whether to take the checkout back to the branch it was on, bring that up to date with `git pull --ff-only` and delete the branch, with `-D` if the pull request was squashed, because git cannot see that a squashed branch has merged. Only a fast-forward: if the base branch has commits the remote does not, say so and stop. If git refuses to switch or to fast-forward over the reader's own changes, say which files and leave them as they are; never stash, reset or force on your own judgement.

Left uncommitted: say which files hold the change, and leave them.

The work is thrown away only when the reader asks for that in so many words, and then only your files, by name, after saying which they are and hearing them confirm. A file the reader had changed too is not put back with git, which would take their changes with yours: say so, and undo your part of it by hand.

Every one of these questions is the reader's, and each goes on a card through `elicitation/create`.
