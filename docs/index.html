Obelus

An editor that fits my own habits — with the agent built in.

Obelus is a code editor, in a window of its own or in a terminal. It is not trying to be a powerful one. It is built around one way of working — mine. If you work the same way, it will suit you too: an agent changes the code on a branch of its own, you read what it did beside the code it changed, and nothing leaves the branch until you say so.

01Is this how you work?

Obelus assumes a particular kind of day. See whether it is yours.

  • You have several projects going at once, and more than one worktree of the same repository
  • An agent writes most of the code; your part is reading it, judging it, and deciding what comes next
  • You keep a list of what comes next, and would rather it sat beside the code than in another app
  • You would rather open a file and read than learn a mode first: arrow keys, Ctrl+c, Ctrl+z
  • You put windows side by side and let your terminal or desktop arrange them

If most of that is you, the rest of this page is what Obelus does about it. If what you want is the most powerful editor there is, start with what it does not do.

02What it does for that

A note becomes a merged change

The agent works on a branch of its own; you read what it did, try it, and say when it goes. The checkout you are reading never moves, and you never type a git command. The Agent screen at the top of this page is one of those days, partway through.

  1. 01

    It starts from a note.

    A line you doubt — Alt+t on it, and a sentence — or a plan with no line under it, written on the notes page (todo from the palette). Either way it is in the project's notes, shared by every worktree of the repository.

  2. 02

    You talk it through with an agent.

    Alt+a on a note opens a conversation about it, and the agent is told what it says. Work out what it would take; the steps you agree to go under the note.

  3. 03

    It changes the code on a branch of its own.

    Before its first change it makes a worktree on a branch named after the change — under .worktree/, where this workflow puts the ones it makes — gets it building and runs the tests once, so a failure afterwards is known to be the change's. The conversation's header says which branch the changes are on.

  4. 04

    It tells you where to try it, and waits.

    It runs the tests again and says the directory and the branch, what it ran and what that showed — not that it should work — and waits until you have tried it. F2 and Tab takes you to that worktree's window; there the change is the newest commit on the branch, and F11 on a line it wrote opens it.

  5. 05

    Nothing leaves before you say so.

    Once you say you have tried it, it asks whether to review the change first — in a fresh context where it can start one — and lists what it found by how much it matters, for you to tick which to fix. Then whether it goes back as a merge, as a pull request, or waits for later.

  6. 06

    A pull request is followed to the end.

    It opens one with gh, follows the checks, says why one failed and fixes it if you ask, and merges once they pass. Without gh signed in, it pushes the branch and hands you the link.

  7. 07

    And it tidies up, asking.

    Once it has merged: if your checkout is on the branch it went into, whether to bring it up to date — a fast-forward and nothing else — and whether to remove the worktree. Once the note is done: whether to tick it off and close the conversation.

Every one of those questions is a card in the conversation, answered with the keys you are already holding. Nothing is pushed, merged, deleted or ticked off because the agent thought it was time.

This is the feature-branch workflow, and it is on unless you set workflow = "none" — Ctrl+p → open-settings → Workflow — after which the agent changes things its own way, usually straight in the checkout you are reading. A project may choose for itself, and one that is not a git repository has no branch to work on, so the agent changes the files where they are. Obelus itself runs no git: every command is the agent's.

Every worktree is one key away

Obelus has no splits: two files side by side is two windows. So several on one project, each on its own worktree, is the normal case. In a window, F2 has a second tab, and Tab goes to it: every worktree git knows of for this repository, wherever it is, with the ones that have a window marked. Choosing one brings its window forward, or opens a new one on it.

Only obg lists them. Going somewhere is starting an Obelus or bringing one forward, and a terminal can do neither: the window it is drawn in is the terminal's, and which terminal you would want a new Obelus started in is not something Obelus can know. So ob has no such tab, and switch-worktree is dim there.

  • Every worktree of a repository opens one set of notes, and what another window writes turns up by itself.
  • Two windows writing at once do not erase each other: every change is made against what is on disk at that moment.
  • A conversation is open in one window at a time, and the claim goes when the process does — no "it did not exit properly last time".
  • A tree removed under a window leaves that window with what was open in it, and the project dim.

A conversation for every note

Obelus has no model of its own. It talks to the agent you already have over ACP, the Agent Client Protocol, and installs one from the protocol's own registry if you have none: F4, a new conversation, the agents page.

  • A conversation is a document in the list of open ones. Leave it and come back tomorrow: it is where you left it.
  • Opened from a note, it stays that note's, and if you reword the note the agent is told what changed.
  • The agent can write the next steps under the note, tick one off, or reword one — each only after asking you.
  • A question is a card, not prose: above it what the agent is going to do, below it the answers, and Enter acts on the row you are on.
  • A change it is asking to make is shown in the conversation; a change it has made is in the file, in the margin, like any other.

Notes that keep their place

Alt+t on a line starts a note about it; todo opens them all. A note can be about a line or about the whole project, and can hang under another. It keeps the commit it was written against as well as the line, so a note written last week still points at what it was written about, however the file has moved. They live in Obelus's own directory, per project — so every worktree shares them, and they never end up in your commits.

Reading what changed

Whatever wrote it, a change is read where it happened: marked in the margin, opened in place with Alt+d, and its history one key away.

git

  • Change marks in the margin, saying what git diff says
  • A map of the file's changes just inside the scrollbar
  • Alt+d opens a hunk in place; Alt+p / Alt+n step between changes
  • Who last changed the line, in the margin (switchable)
  • The file's history F9, the project's F10, the commit that wrote this line F11; a commit's message hangs above its file, and what the remote has not seen is marked
  • Read-only: Obelus never changes your repository, and runs no git for you

In a terminal, or in a window

  • obg is a window and ob is the terminal — gvim's relation to vim, not a second program: the same grid, the same views, the same keys
  • The window is for the two things a terminal cannot give. It cannot tell Ctrl+i from Tab, Ctrl+m from Enter or Ctrl+[ from Esc — one byte each — and most send nothing at all for Ctrl+Shift+X
  • And it draws with a font it carries rather than one it hopes you installed: the marks are compiled in, so there are no boxes and no switch to find
  • It draws its own pixels, so the caret and the lists move rather than jump, and what an input method is spelling is on the page before it is a character

A file, read more than one way

  • Markdown laid out as prose (Ctrl+t), a log put in columns — decided by what the lines look like, not by the file's name
  • The code in a markdown fence and the script in an HTML page are each highlighted as what they are
  • Long lines break the way their language does: Chinese between characters, an English word never cut in half, continuation rows keeping the indentation
  • And the ordinary things: twenty-three languages, folding, soft wrap

Asking about the code

  • What an IDE answers — where a name is defined, who calls it, what it is, what is wrong — asked of the language server you already have: rust-analyzer, gopls, clangd, pylsp and the rest
  • One view for finding, at three radii: this file F5, every file F6, the names a server knows F8 — and Alt+← goes back to where a jump began
  • A server is not the only thing that finds a problem: what Obelus cannot make of its own settings is marked on the line it could not read, in the same list

Keys without modes, in a window or a terminal

Every key means what it says whenever it is pressed — the VS Code and Emacs way, not the vim and helix one. Function keys open something to look at, Ctrl does something to the file in front of you, and Alt asks about the cursor. Ctrl+p finds any command by name, and Ctrl+k lists every key the view in front of you takes. The full table is in the reference.

03What it does not do

On purpose, and not for want of getting to it.

  • No multiple cursors, macros or snippets. Large edits are the agent's job now; what is here is what fixing a line on the way past needs.
  • No splits. Two files side by side is two windows; your terminal or window manager tiles better than an editor can from the inside.
  • No modes. No vim or helix keys, and no switch to turn them on.
  • No git writes of its own. Obelus reads git and never writes it. When a change goes somewhere, it is the agent running git — after asking you.
  • One agent at a time. Two would mean every question having to say which agent it was for.
  • No model of its own. It talks to the agent you already have.

If any of those is a reason you choose an editor, Obelus will not suit you — and that is fine. It was not built to.

04Principles

The sentences the trade-offs are decided against. Most were written down after getting it wrong once.

  1. 01

    It fits one way of working, not a checklist.

    A feature is in because it is what that way of working reaches for, not because editors are expected to have it.

  2. 02

    What an agent does, you can see and take back.

    A write it makes goes through the file as one change, and Ctrl+z undoes it. A command it runs cannot be undone, so it is shown in the words it was actually run in, with everything it printed, and the key that stops the agent stops the command too.

  3. 03

    A change that has happened is in the file; one still being asked for is in the conversation.

    Once an agent has edited a file, the margin already draws the difference; drawing it again in the transcript would be a second account of one thing. What it is asking to do goes in the transcript, and stays there.

  4. 04

    A file being rewritten while you read it is the normal case.

    An agent edits the file you have open, a formatter runs, a branch changes underneath you. So Obelus re-reads by itself, without losing your place, and a file that has gone is marked [stale] and keeps its contents on screen.

05Why it exists

Honestly: I wrote it for myself. Every trade-off answers "does this work for me" before "will somebody refuse it without feature X" — which is why the habits on this page are mine.

I never got comfortable with vim. Modes, hjkl, colon commands — muscle memory for the people who have it, and for me something to work out again every time. I wanted to open it and read: arrow keys are arrow keys, Ctrl+c copies, and nothing has to be escaped out of first.

And the way I work changed. A pile of claude code and codex sessions write most of the code; what I do in front of the screen is read, check, mark what looks doubtful, and decide what comes next — with a todo list I wanted beside the code rather than in another app. The editors in a terminal compete on an editor's list. Obelus is an editor too, but it is on another line: the syntax tree, the git timeline, the language server and the agent, arranged the way I work.

06Getting started

Install

One script per shell, and which you want is which shell you are in. Either one takes the latest release, checks what it downloaded against the release's own SHA256SUMS, and puts obg where your PATH can find it — Obelus in a window of its own.

Linux and macOS

curl -fsSL https://raw.githubusercontent.com/obelus-editor/obelus/master/contrib/install.sh | sh

Windows, in PowerShell

irm https://raw.githubusercontent.com/obelus-editor/obelus/master/contrib/install.ps1 | iex

The terminal one as well

ob is the other binary and is asked for by name. Everything after -s -- goes to the script; a pipe into iex has nowhere to put an argument, so on Windows the script is fetched first instead.

curl -fsSL https://raw.githubusercontent.com/obelus-editor/obelus/master/contrib/install.sh | sh -s -- --bin both
irm https://raw.githubusercontent.com/obelus-editor/obelus/master/contrib/install.ps1 -OutFile install.ps1
.\install.ps1 -Binary both
  • --bin ob is the terminal one on its own, --dir says where to put it, and --help lists the rest.
  • The releases carry an archive for every platform, and a .deb, an .rpm, an AppImage and a macOS .app.
  • On Windows the script adds its directory to your PATH and puts Obelus in the Start menu; -NoShortcut leaves the menu alone. The shell script says which line to add if the directory is not on your PATH already, and on Linux it adds a desktop entry for each of obg and ob that it installed — ob's opens in a terminal — and an icon, under ~/.local/share, which every launcher reads, omarchy's Apps menu among them; --no-desktop leaves them out.
  • -Uninstall takes back the binaries and the Start menu entry, and the directory and its PATH entry where nothing else is left in it. --uninstall, with the same --dir it was installed with, takes back the binaries, the desktop entries and their icon, and on omarchy the theme template — and leaves the PATH, which it never changed. Neither touches your settings.
  • On musl there is no obg: the window finds Vulkan, Wayland and X11 by dlopen, which a static binary cannot do, so the script says so and installs ob.

From source

Which needs nothing but a stable Rust toolchain (edition 2024).

git clone https://github.com/obelus-editor/obelus
cd obelus

# installs as `obg` into ~/.cargo/bin: Obelus in a window of its own
cargo install --path crates/obelus-gui

# installs as `ob`: the same editor, in the terminal
cargo install --path crates/obelus-cli

# or just build them: target/release/obg and target/release/ob
cargo build --release

Worth having as well

  • A Nerd Font, for the glyphs beside a file's name and on the status bar — in the terminal. They are off until icons is turned on, so without one no boxes appear. obg needs none of this: it carries the marks in the binary.
  • A language server for your language (rust-analyzer for Rust). Without one, reading still works — there is just no definition, no diagnostics, no outline.
  • An ACP agent. Obelus can install one from the registry — see a conversation for every note.

Run it

obg                  # nothing: the welcome screen, on this directory
obg src/main.rs      # read a file — its repository is the project
obg ../another-repo  # a directory: that is the project
ob src/main.rs       # the same file, in the terminal instead

The first five minutes

  1. F1 opens a file. Type to narrow, ↑↓ to choose, Enter to accept, Esc to cancel.
  2. Not sure which keys a view takes? Press Ctrl+k. The row at the foot lists what is available now; Ctrl+k opens all of them, with the rest greyed out.
  3. Ctrl+p is the command palette: anything you cannot remember a key for is findable by name.
  4. Put the cursor on a change and press Alt+d: the hunk opens in place, with what was there before it.
  5. See a line you doubt: Alt+t, and write a sentence. It goes in this project's notes, and todo brings them all back.
  6. Ctrl+p → open-settings for colours, wrapping, tab width; choose-theme for the theme.
  7. Ctrl+q leaves.

Every key, command and setting is in the reference.
